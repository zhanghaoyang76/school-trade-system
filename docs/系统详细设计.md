## 分层及框架使用

| 部分 | 职责与实际机制 |
|---|---|
| Vue页面及组件 | 展示、路由、表单、上传、调用API和错误反馈 |
| Controller与请求对象 | 接收REST参数并校验格式，不直接写SQL或扣款 |
| 登录及权限拦截器 | 从Session取得用户编号，检查接口允许角色 |
| Service | 校验资源归属、审核状态和交易资格，管理事务及状态转换 |
| Mapper与XML | BaseMapper处理基本CRUD，XML实现动态搜索和关联统计 |
| Entity | 对应数据库表，不直接将完整用户实体返回给页面 |
| 统一异常处理 | 参数、权限、业务冲突和系统错误转为一致响应 |
| AOP审计 | 拦截明确标注的资料修改、管理员审核和充值等成功操作，保存脱敏记录 |
| IoC与DI | Spring创建各层Bean，构造器注入依赖，便于隔离测试 |
| 自动配置 | 使用Spring Boot数据源、Web、Session等配置，不重复手工创建容器 |
| 定时任务 | 扫描可处理订单及积分，事务内条件更新，支持重复执行 |

服务内按业务模块组织文件，保留Controller、Service、Mapper、Entity清晰职责，不引入微服务。定时任务和HTTP入口调用同一业务服务，避免两套结算逻辑。

## 账户与图片

- 公开接口只允许验证码、注册、登录、已上架商品及公开店铺查询；涉及购物车、订单、钱包和卖家操作均须登录并通过审核。
- Session仅存必要身份标识，关键请求重新检查账号是否有效；密码以强单向哈希保存，不在日志或响应返回密码摘要。
- 生产使用同源部署；开发时由Vite代理API。Session Cookie设置HttpOnly和适当的SameSite属性；状态修改请求校验跨站请求伪造令牌。
- 银行账号为16位数字的字符串，不能用数值类型丢失前导零；展示时遮盖中间位数。
- 上传校验文件内容、类型、大小和所属用户，使用随机存储名；商品图公开，营业执照及身份证仅本人及管理员可读，禁止用静态目录直接暴露所有证件。
- 注册资料与证件关联写入用户记录；注册审核拒绝时保留明确原因。

## 订单与售后状态

已确认主流程：结账按卖家拆单并统一扣款 → 待线下交付 → 已交付待确认 → 确认收货并结算冻结 → 无退货且满24小时后解冻。

交付前允许买卖任一方取消，退实付款及抵扣积分、恢复库存。自动收货从卖家标记交付开始计算7天。自动收货产生的确认时间同样启动24小时退货期限。

已确认售后：确认收货后24小时内申请整项退货 → 卖家审核 → 通过即退款并标为在途退货 → 卖家确认收到退货 → 恢复库存并标为已退货。未交回商品不恢复库存。

每个订单明细单独记录售后与资金解冻，避免一个商品退货影响其他商品；重复申请及重复审核不能导致重复退款。订单及快照保存历史，不随商品编辑变化。

## 已确认的金额规则

- 下单扣钱包实际付款，记录平台托管；卖家确认收货后按订单保存费率收手续费，净收入转卖家冻结余额。
- 个人卖家手续费为0；商家费率按已确认的五档计算并四舍五入到分，等级变化不追溯旧单。
- 无售后且24小时结束，卖家收入及买家奖励积分转可用；售后中继续冻结该明细。
- 退货时从卖家对应冻结收入及平台已计手续费还原该明细实付款，退回原抵扣积分，取消该明细奖励积分。
- 1元实际钱包支付产生1积分，100积分抵1元，允许抵完商品金额，不支持购买积分。
- 钱包和积分均记业务流水，业务唯一标识防重；钱包可用、冻结、平台托管及手续费余额必须能对账。

## 已确认补充规则

以下10条补充规则已随本文件整体获用户确认：

| 编号 | 提案 | 原因及影响 |
|---|---|---|
| 补01 | 普通用户、商家均可购买其他店铺商品，不可购买自己的商品；管理员账号仅做管理 | 防自买刷流水，角色职责清楚 |
| 补02 | 用户删除采用逻辑删除，停用登录并关闭其店铺、下架商品，保留已有订单、流水和评价；存在未完成订单或待处理售后时拒绝删除，先完成处理 | 防历史交易断链及无人处理售后 |
| 补03 | 商品修改名称、类别、价格、描述或图片后重新审核，审核前不可接受新订单；已有订单不受影响 | 避免审核后更换为未审核内容 |
| 补04 | 允许议价只展示标识和说明，双方线下协商后由卖家修改售价并重审，再按页面售价下单，不另做聊天或在线报价系统 | 课程只要求议价标识，保持功能简单 |
| 补05 | 确认收货后可评价，每个商品明细每个方向一次，不支持修改、匿名或追评；退货成功后原评价仍保留且不重复评价 | 保留真实交易反馈，不追加未选功能 |
| 补06 | 无商品或服务评价时展示“暂无评价”，排序按好评率0处理并以商品编号作稳定次序；4至5星为好评 | 无评价不能伪装成100% |
| 补07 | 审核拒绝退货必须填写原因；仍在收货24小时内可重提，超过期限不能新申请。拒绝且期限已到则解除该明细冻结；已通过的售后即使超时仍可完成交回 | 明确拒绝后冻结何时解除 |
| 补08 | 积分抵扣降低卖家收到的成交额，平台不额外补贴。例如100元商品用100积分抵1元，则钱包付99元，按99元结算和计算手续费、奖励积分 | 明确积分优惠由谁承担，避免凭空产生货款 |
| 补09 | 整次结账抵扣积分须为100的整数倍；优惠金额按明细原金额占比分摊到分，尾差依明细编号分配，任何明细不抵成负数。分摊到1分钱对应退回1积分；奖励积分按明细实付款向下取整 | 每项均可独立退款，总抵扣、退款及发积分可核对 |
| 补10 | 审核中的账号只能获知登录被拒原因；注册审核拒绝后可用原账号和密码及新验证码重新提交资料，不开放正式购物登录 | 允许修正材料，同时满足审核通过后才能使用 |

## 数据模型

使用《数据库设计》中的17张表：users、shops、categories、products、product_images、uploaded_files、cart_items、checkout_batches、orders、order_items、return_requests、reviews、blacklists、wallets、wallet_entries、point_entries、audit_logs。

用户表补充营业执照和身份证文件编号、审核意见；积分分可用与冻结；资金按用户账户、平台托管账户、平台手续费账户分别记账。金额DECIMAL，Java用BigDecimal；库存及积分使用整数。订单保存商品、金额、费率及买卖双方必要快照。

先按固定顺序锁定涉及的商品与账户，再执行资格校验、扣库存和扣款。采用数据库事务、带状态条件的更新、唯一业务键，防止超卖、重复确认、重复退款。结账幂等键由客户端同一次结账复用，不能每重试一次生成新键。

## REST接口分组

统一前缀`/api`。成功返回业务数据及消息，列表返回记录和总数；失败使用实际HTTP状态码，参数错误400、未登录401、无权限403、资源不存在404、余额库存或状态冲突409，系统故障500。分页、排序字段使用白名单，不拼接任意SQL。

## 关键验证与交付标准

1. 注册校验、验证码失效与审核，个人卖家和商家分别走通真实页面。
2. 商品多图审核、店铺、名称搜索和三类排序，直接接口越权也被拒绝。
3. 跨店结账任一失败全回滚，同一结账重试不重复扣款，最后一件并发购买仅一方成功。
4. 充值、托管、确认、冻结、解冻、手续费及退款逐笔可核对；重复任务和重复退款不改变资金总额。
5. 自动收货验证交付后7天边界；退货验证确认后24小时的前后边界、待审冻结、立即退款与交回后恢复库存。
6. 积分获得、抵扣、冻结、返还及取消奖励，以及跨商品分摊尾差。
7. 等级门槛、无评价、手动覆盖与恢复；商家及平台拉黑、关店、恢复、已有订单不受错误限制。
8. 前端浏览器实测主流程与手机布局，上传私有文件不可越权读取，正式业务结果以数据库和接口为证。
9. 提供从空数据库启动的步骤、配置样例、实际执行命令及结果、问题记录、主要提示词和逐模块讲解。
