# 模块讲解

本文件按已实现的代码讲解业务、数据流、框架和答辩要点，供学习与现场演示使用，不是实验报告正文。先运行平台并实际操作，再结合源码阅读。

## 一、先理解整体数据流

浏览器中的Vue页面通过`frontend/src/api.js`请求`/api`。开发时Vite把请求代理至8080，Cookie携带Session标识。`Security`拦截器验证登录与角色，Controller接收请求，Service检查业务和数据归属，通过Mapper访问MySQL，返回JSON供Vue响应式更新页面。

Controller不处理扣款、退款，不直接执行SQL。`ApiEndpointService`及`AdminEndpointService`组织接口查询，`AccountService`、`CatalogueService`、`TradeService`、`AdminService`承担相应业务。`campus.mapper.Store`是参数化DAO适配层，实际委托MyBatis `SqlMapper`；商品写入使用真正的`ProductsMapper extends BaseMapper`，搜索使用`CatalogueMapper.xml`。

**答辩要点：** Entity是数据库实体，DTO或安全Map用于响应；用户实体含密码摘要和证件信息，不能原样返回前端。前端路由守卫用于用户体验，服务端校验才是权限边界。

## 二、注册、验证码与登录权限

**业务：** 普通用户通过审核即可买卖，商家还需营业执照与身份证。银行账号为16位数字，所有注册者先待审。图片验证码防止无成本重复提交，审核未通过不能正式登录。

**代码：** `AccountService.captcha/register/login/profile`、`Security`、`AuthPage.vue`、`state.js`。

**数据流：** 获取验证码图片及Session → 提交资料与验证码 → 密码BCrypt哈希入库 → 管理员审核 → 登录成功将用户编号保存在Session，浏览器仅持会话Cookie。每次受保护请求重新核对账号审核和删除状态，不能只信旧会话。

修改请求还携带CSRF令牌，防止其他站点借已有Cookie伪造充值或下单。退出失效Session，前端清缓存令牌，下次修改重新获取。银行账号用字符串，保留前导零；响应遮盖中间位数。

**验证及答辩：** 尝试待审登录、错误验证码、未登录调用后台、删除用户后沿用旧Session。说明“用户身份鉴别”和“是否允许执行此操作”是不同校验。

## 三、图片、商品与店铺

**业务：** 商品有多图、原价、折扣、售价、数量、尺寸、说明、成色及议价标识，发布或修改后需要审核。关店禁止新发布与新购买，不影响已有交易。

**代码：** `FileController → FileService → Store/SqlMapper`，`CatalogueService`、商品Entity与BaseMapper、`UploadField.vue`、`SellerPage.vue`。

**机制：** 文件检查大小和内容，重新编码为PNG并以随机名存储，数据库仅保存元数据和关联编号。商品图片可以公开读取；证件必须验证本人或管理员，不能把整个上传目录映射成无权限静态资源。

售价由原价乘折扣系数计算，如0.8表示八折；后端BigDecimal四舍五入至分。前端计算只是即时展示，后端会重新计算。修改后的商品重新待审，已经生成的订单使用商品快照。

**验证及答辩：** 上传两张图并审核；修改售价后确认停止新购买；旧订单金额不变；另一个普通账号不能获取他人证件。个人卖家同样有店铺列表，但没有收费等级。

## 四、名称搜索与排序

**代码：** `CatalogueMapper.xml`的`<if>`按名称、店铺、类别组合条件，`<choose>`仅允许价格升降、销量和好评率排序，默认用编号保持稳定次序。

`#{keyword}`是绑定参数，不是字符串拼接。不能让浏览器直接传入一段ORDER BY SQL。销量和好评来自订单及评价关联查询；无评价展示“暂无评价”，不能填默认五星。

**验证及答辩：** 同一关键词跨店铺返回多件商品，切换三类排序并核对顺序；分页切到下一页。解释BaseMapper适合基本CRUD，XML更适合条件组合及关联统计。

## 五、购物车、跨店结账及库存

**代码：** `CartPage.vue`、`TradeService.checkout`、购物车和订单相关表。

**业务流程：** 购物车选择 → 每店约定交付时间地点 → 统一校验账号、店铺、拉黑、库存、钱包和积分 → 按卖家生成订单 → 扣钱包、积分及库存并记录平台托管 → 一次事务提交。

`@Transactional`通过Spring代理将这批数据库写入作为一个事务。任一商品不满足条件即抛业务异常，前面已扣的库存与款项一并回滚。数量合并使用溢出检查，不能让大整数相加变成负数从而反向增加库存。

同一次结账请求携带稳定的幂等号，网络超时后重试返回同批订单，不再扣款。数据库唯一约束和事务内查重共同防重复。库存操作使用行锁及数量条件，最后一件商品不能被两人同时买走。

当前单体课堂项目用平台托管账户行作为共享事务锁，统一资金相关锁序以降低死锁风险。它以吞吐量换清晰正确性，不是分布式高并发设计。

**验证及答辩：** 一个购物车商品不足时整次失败；两个请求抢最后一件只成功一个；相同幂等号重复提交只扣一次。说明“先查询库存再无条件扣减”为什么有竞争窗口。

## 六、钱包、手续费、积分与资金冻结

**代码：** `TradeService.entry/points/confirm/release`、`wallets`、`wallet_entries`、`point_entries`、`WalletPage.vue`。

下单：买家可用余额减少，平台托管账户增加。确认收货：托管账户减少，卖家冻结收入及平台手续费增加。24小时无售后：卖家冻结减少、可用增加。充值由管理员执行，产生资金流水。

例如商品100元，用100积分抵1元，钱包付99元。商家1级费率0.1%，手续费按分四舍五入为0.10元，卖家冻结收入98.90元；买家新获得99积分，但先冻结。个人卖家免手续费，收到99元。优惠由卖家承担，平台不会额外生成1元补贴。

订单保存下单费率，不因商家后来升级改变旧单。每个明细保存分摊实付款、抵扣积分、奖励积分和手续费，确保只退某项时不影响其他商品。抵扣总额按比例到分分摊，尾差顺序固定，总额必须守恒。

**验证及答辩：** 对比每笔可用及冻结变动和平台托管、手续费；余额不够不能下单。金额使用BigDecimal及数据库DECIMAL，不能用浮点数做钱款结算。

## 七、交付、自动收货、取消与退货

**代码：** `TradeService.cancel/delivery/confirm/requestReturn/reviewReturn/receipt/release`、`AdminService.tasks`，`OrdersPage.vue`与`ReturnsPage.vue`。

交付前任一方可说明原因取消，退实付款和抵扣积分并恢复库存；卖家标记已交付后不能再直接取消。交付后7天买家仍未确认，定时任务调用相同确认服务。确认后开始24小时退货窗口。

退货按商品明细整项申请，同明细买多件一起退。卖家通过时立即退款并冲回手续费、原抵扣积分和奖励积分，状态为“在途退货”；实际交回后卖家确认，库存才恢复，状态为“已退货”。拒绝须填写原因，期限内可重提；待审核不能提前解冻。

**框架要点：** Spring定时任务每分钟扫描符合条件的记录；真正状态转换在事务服务中，采用旧状态条件及唯一流水防重。测试通过调整测试记录的时间验证边界，不需要真的等待7天，也不能把测试时间改写成真实等待记录。

**验证及答辩：** 收货24小时前后分别申请，重复确认和重复退款不可多打款；退货审核通过后立即看买家余额，但在卖家收回商品前库存不变。

## 八、评价、信用与商家等级

买家对商品及服务分别五星评分并写文字，卖家对买家的购买／退货行为评分；4至5星计好评，各自统计，不混成一个比率。确认收货后可评价，每个明细每个方向一次，不做匿名或追评。退款后保留真实交易评价。

`AdminService.recalculate`根据退货期结束未退货成交额和服务好评率计算等级；5档门槛见需求记录。管理员手动指定后设为MANUAL，自动任务最终UPDATE还检查AUTO条件，防止任务先读后写覆盖刚设置的手动等级。

**验证及答辩：** 无评价保持1级；达到成交额但好评不足不能升级；手动指定后自动计算不得覆盖；恢复AUTO后重新计算。课程费率随等级升高而增加，不能自行解释为越高级越优惠。

## 九、管理员、关店与黑名单

**代码：** `AdminController`、`AdminEndpointService`、`AdminService`、`AdminPage.vue`及`BlacklistPanel.vue`。

审核只能作用于待审记录，用户修改及删除记录脱敏操作；有未完成交易的账号不能删除，删除保留历史记录且不能重新开店接单。管理员充值、设置等级和查看收费记录。

商家黑名单只影响本店，平台黑名单影响全平台；均可解除，不剥夺旧订单和售后。跨店结账包含禁止购买的商品时整体失败。关店把商品下架，恢复营业后原商品需重新审核。

**验证及答辩：** 直接调用别家接口必须失败；拉黑前订单仍可收货退货；重新开店不会自动把所有旧商品上架。解释为什么服务端必须重复检查，而不能只隐藏“购买”按钮。

## 十、IoC、AOP、异常处理与前端机制

- IoC/DI：Spring创建标注Service、Repository、Controller的对象，通过构造器注入依赖；测试可启动相同容器验证事务和Mapper。
- AOP：`AuditAspect`通过`@AfterReturning`拦截成功的`@Audited`操作，写操作人、对象及变更字段名，不记录密码、完整银行账号或证件内容。它不自动替代业务权限检查。
- 自动配置：`@SpringBootApplication`启用组件扫描和自动配置，结合starter及application.properties配置Web、数据源等；`@MapperScan`发现Mapper。
- 统一异常：`BusinessException`及ControllerAdvice映射400、401、403、404、409、500，前端展示后端原因，不能把异常HTTP200当成成功。
- Vue响应式：ref/reactive改变数据后更新模板；Router按角色和路径组织页面。路由切换时给异步请求加版本号，迟到响应不能覆盖当前商品或后台审核对象。
- Element Plus：提供输入、表格、对话框等组件，统一中文反馈；原因验证器必须对有效输入返回true，返回字符串代表错误提示。
